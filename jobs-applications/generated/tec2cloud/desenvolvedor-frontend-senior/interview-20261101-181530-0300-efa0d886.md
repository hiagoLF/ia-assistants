## Technical interview

### 1. How have you used Vite, and what does it change?
**Personal evidence:** “I used Vite in most React web projects I worked on, including Knowledge Paths.”
**Conceptual answer:** Explain the difference between the development server and a production build, module resolution, environment configuration, asset handling and TypeScript checking. A successful bundle does not replace a dedicated type-checking step. Values embedded in a browser bundle are public; environment variables do not make secrets safe.
**Follow-up:** How would you debug a build that succeeds locally but fails in CI? Compare Node and package-manager versions, lockfiles, environment variables, filename casing and the exact failing command. Tool behavior depends on the project's installed version.

### 2. How would you organize an application with Feature-Sliced Design?
**Personal evidence:** “I used FSD in Allp Fit while developing an app-feedback feature. Organizing code around explicit feature boundaries made exploration easier.”
**Conceptual answer:** Describe responsibilities and dependency direction between app composition, pages, widgets, features, entities and shared foundations. Explain public interfaces and avoid importing implementation details across slices. Keep abstractions proportional to product complexity; a small utility does not need an elaborate hierarchy.
**Follow-up:** Where do the feedback form, submission workflow, API adapter and reusable input belong? Explain ownership and dependencies rather than forcing every file into a generic folder.
**Metric boundary:** The 50% reduction in agent exploration time was a personal estimate. Present the benefit qualitatively.

### 3. How do you handle i18n and localization?
**Personal evidence:** “All MB Labs projects I worked on used i18n for text. For date and currency handling, I used native JavaScript APIs or Luxon with shared helper functions. I displayed the user's time zone and used a fixed time zone for exchanges with the backend.”
**Conceptual answer:** Separate translated text from locale-sensitive formatting. Explain translation keys, interpolation, plural rules, fallback locales, locale switching and testing. Prefer full messages over concatenating translated fragments. Currency choice and display locale are separate business inputs.
**Boundary:** No specific i18n library, pluralization implementation or catalog-management workflow was confirmed. Discuss those as design knowledge, not completed personal work.

### 4. How would you prevent time-zone bugs?
**Conceptual answer:** Distinguish an instant, a calendar date and a recurring local time. Agree with the backend on a precise wire format and zone/offset convention. Convert instants for display in the user's zone, and test day-boundary and daylight-saving transitions where relevant. A date-only field such as a birthday should not shift because it was accidentally interpreted as an instant.
**Personal boundary:** A fixed exchange time zone was confirmed; UTC was not specified. Do not say the existing project used UTC unless verified.

### 5. How do you apply TDD?
**Personal evidence:** “I use TDD and work with React Testing Library, Jest and Vitest. For E2E testing, I use Playwright on React web and Detox on React Native.”
**Conceptual answer:** Start from an observable behavior, write a failing test, implement the smallest change that passes and refactor while retaining coverage of the behavior. For a feedback feature, test submission, validation and failure/retry paths using accessible user interactions.
**Follow-up:** When is TDD less useful? Explain exploratory spikes and uncertain interfaces, then how you establish stable tests once behavior is understood. Do not equate every test written with test-first development.

### 6. What belongs in unit, component, integration and E2E tests?
**Conceptual answer:** Unit tests cover isolated rules and helpers. Component tests cover visible UI behavior. Integration tests cover cooperating boundaries such as a form, state and an API adapter. E2E tests exercise critical user journeys through the application. Use deterministic data and controlled external dependencies; avoid making every case an expensive browser test.
**Follow-up:** How would you test localized currency, a failed request, a loading state and a time-zone boundary? Explain the assertion at each level and why duplicate tests may not add value.

### 7. How do you keep React state and effects manageable?
**Personal evidence:** The profile includes React Hooks, Redux, Zustand and React Hook Form.
**Conceptual answer:** Keep state local unless it must be shared. Distinguish form state, server data and cross-screen client state. Derive values during rendering when possible rather than storing duplicated state. Use effects to synchronize with external systems; handle cleanup, stale responses and request cancellation. Profile before adding memoization.
**Follow-up:** Why might a list still re-render after memoization? Discuss unstable object/function references, context updates, changed props and whether memoization costs exceed the work saved.

### 8. How do you integrate REST APIs safely?
**Personal evidence:** API integration is supported by the original profile.
**Conceptual answer:** Model loading, success, empty and failure states explicitly. Validate assumptions at runtime because TypeScript types do not validate network responses. Handle cancellation, stale requests, authorization failures and safe retry behavior. Avoid logging tokens or sensitive response bodies. Explain ownership of client state versus server state.
**Boundary:** Security practices here are conceptual; no specific security project was reported.

### 9. How do you make interfaces accessible?
**Personal evidence:** The semantic HTML skill improved average Lighthouse accessibility scores from 30 to 90 on the pages addressed.
**Conceptual answer:** Prefer native elements with meaningful labels, logical headings and alternative text suited to the image's purpose. Preserve visible focus, logical tab order and keyboard operation. Avoid positive tabindex values and make custom widgets only when native controls cannot serve the purpose. Review contrast, zoom/reflow and screen-reader behavior alongside automated checks.
**Correction:** Do not remove outlines without preserving an accessible visible focus indicator. The confirmed workplace rule was never to use `outline: none`.

### 10. When does virtualization help, and what are its trade-offs?
**Personal evidence:** react-window reduced measured long-list re-rendering time by approximately 50%.
**Conceptual answer:** Virtualization limits mounted rows to a visible window plus a buffer. It can reduce DOM and rendering work, but introduces complexity around variable heights, focus retention, assistive technologies, browser search and scrolling. Compare it with pagination and reducing per-row work. Re-profile representative user interactions after the change.

### 11. What CI/CD checks have you configured?
**Suggested personal answer:** “I worked with Bitbucket Pipelines and GitHub Actions and also with Azure and automated deployment tools. I configured linting, type checking and Jest/Vitest test execution as pipeline checks.”
**Conceptual answer:** Explain reproducible dependency installation, explicit runtime versions, separate validation/build/deploy jobs, protected secrets, environment approvals when appropriate and a tested rollback approach. Scope browser tests to critical journeys and investigate flakiness.
**Boundary:** Azure DevOps was not explicitly confirmed. The estimate of up to 90% fewer deployment errors is not a measured result and should stay out of quantitative claims.

### 12. How do you investigate production errors?
**Suggested personal answer:** “I integrated Sentry and Crashlytics to capture frontend errors and improve diagnostic context. The support team reported 60% fewer user complaints, which they associated with earlier bug reports and better information for investigation.”
**Conceptual answer:** Triage by user impact, reproduce with relevant context, correlate with releases, inspect stack traces and validate a fix. Discuss source maps, privacy-conscious logging and alert noise as design considerations.
**Boundary:** The metric concerns complaints, not a measured reduction in crashes. Do not claim a controlled causal experiment.

### 13. What frontend security risks would you consider?
**Conceptual answer only:** Discuss XSS and unsafe HTML rendering, URL validation, dependency risk, secrets accidentally bundled into client code and the limits of client-side authorization. Explain that CSRF, cookies, CORS and token storage depend on the application's authentication design. Coordinate with backend/security owners instead of inventing a universal solution.
**Honest framing:** “I would assess these risks against the application's threat model. I have not provided a specific security-hardening project as an example here.”

### 14. How would you review a pull request?
**Conceptual answer:** Start with the intended behavior and user impact; then check boundaries, state transitions, failure paths, accessibility, localization and whether tests cover the important behavior. Separate correctness issues from preferences. Explain the reason for requested changes and agree on conventions.
**Boundary:** Architectural leadership is confirmed, but a specific code-review history was not supplied. Do not turn this conceptual answer into an invented anecdote.

### 15. Design an international feedback feature.
**Practice scenario:** A React/TypeScript/Vite app needs a localized feedback form, accessible keyboard interaction, backend submission and reporting.
**Suggested approach:** Clarify locales, authentication, privacy and success criteria. Define FSD boundaries and typed API contracts. Model idle, submitting, success and failure states. Use accessible labels and localized validation messages. Define event-time storage and display separately. Write behavior tests for validation, submission, failures and locale changes; add a focused E2E journey. Include lint/type/test checks in CI and propose error monitoring without collecting sensitive feedback content unnecessarily.
**Trade-offs:** Do not add a global state store for a single local form without a reason. Discuss retry/idempotency and whether optimistic updates fit the interaction.
**Personal bridge:** Connect this to the Allp Fit feature, while distinguishing hypothetical design choices from details of that implementation.

### 16. Explain the Knowledge Paths result.
**Suggested personal answer:** “I developed the frontend of a Knowledge Paths module that gave students a visual roadmap of lessons, exercises and materials. The module used React, Next.js and React Native, and Vite was also used in the Knowledge Paths work. Consumption of learning materials increased by five times.”
**Prepare before interview:** Clarify which web application or package used Vite and which used Next.js; do not imply they were the same build pipeline. Prepare the baseline, measurement period, metric source and your contribution versus other team members. The supported result is 5x material consumption, not 4x engagement.

## Final practice checklist

- Prepare one precise architectural decision, its alternatives and the outcome.
- Bring anonymized evidence for Lighthouse and React profiling measurements where available.
- Verify the source, baseline and time window of historical business metrics before discussing them in depth.
- Keep estimates separate from measured results; attribute the complaints metric to support.
- Be explicit about the first international-team transition and the unconfirmed Azure DevOps, security and code-review details.
- Confirm compensation, availability, contract terms and time-zone overlap before using an answer with specifics.
